Warden

Enforcing What AI Agents Can Do Below the Shell
Arkar Myat (Computer Science), May Aung (Computer Systems Technology), Professor Lawrence Ryan (Data Science)
[City Tech logo]
01

Abstract

LLM agents increasingly execute shell commands, but prompts and userspace command filters reason about text while damage occurs through system calls. Warden is a small x86-64 research kernel that labels every agent process with a session, capability set, and writable filesystem scope; labels persist across fork and exec, and a fail-closed dispatch table checks every system call. We validate the current prototype with host unit tests and end-to-end QEMU tests, and plan an 80-run comparison of prompt-only, userspace-filter, kernel-only, and combined configurations on 20 tasks. The current implementation passes all 57 available test groups (11 host binaries and 46 in-kernel tests). Comparative safety, utility, and overhead results have not been measured yet.

02

Introduction & Background

Coding and operations agents act through tools such as run_shell(command), which can create, modify, execute or delete files with the authority of the user who started the agent. The AgentDojo benchmark contains 629 security test cases across 97 realistic tasks [1].

Most systems rely on prompt rules or a userspace wrapper that rejects suspicious command strings. Both act before the shell interprets the command. A shell can build the same action through quoting, variables, cd, path traversal, scripts or child processes.

A filter looking for /bin misses:
$ cd /; rm b''in/ls
kernel receives → unlink("/bin/ls")

Warden makes the decision in the kernel. At that point the kernel knows the calling process, the requested system call and the normalized path, no matter how the command was typed.

Research questions
  1. Security. Which escape techniques are blocked by prompt rules, a userspace deny-list, kernel enforcement, and both combined?
  2. Utility. How does kernel enforcement affect task success and unsafe actions attempted vs. executed?
  3. Overhead. What does the capability check cost per ordinary and path-based system call?
03

Methodology

  1. An operator sends a request to bridge.py; the model returns exactly one run_shell call via an OpenAI-compatible API.
  2. The bridge forwards the command over a Unix socket to QEMU's COM2; /dev/agent delivers it to agentd.
  3. agentd forks. The child redirects output to a pipe, calls mark_agent(session, caps, scope), and only then runs /bin/sh -c.
  4. The label is inherited across fork, kept across exec, and can only narrow. Every syscall passes one dispatch table; paths are checked after normalization.
  5. The parent streams output back, ending with \0EXIT <code>. agentd never executes agent input itself.

05

Discussion

After a child process is labeled, writing the same shell command in a different way does not change what that process is allowed to do. Path traversal and prefix tricks fail because paths are checked after normalization. Attempts to widen a label fail because labels can only narrow.

agentd keeps its human label, so the trusted code stays small. It labels only the forked child before exec. If labeling fails, the child exits with status 126.

Limitations. These results do not yet show that Warden outperforms prompt rules or a deny-list. The kernel has no network, symbolic links or kernel-managed working directory, and the pilot uses 20 author-written tasks, one model and one repetition per configuration.

06

Conclusion & Future Work

An agent's permissions can follow its processes across fork and exec and be checked at one kernel entry point. The kernel does not need to parse command text.

  • Run the escape suite, 80-run pilot and microbenchmarks.
  • Add file-writer provenance, per-session limits and a session-wide kill switch.
  • Expand to more tasks, at least two models and repeated trials.
